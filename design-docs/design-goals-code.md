# Design goals: the `code` skill

This skill governs every task whose deliverable is code - writing, editing, reviewing, refactoring, debugging, designing schemas or infrastructure. It exists to make one idea operate on that work: design the constraints so illegal states can't be expressed, and the implementation falls out as residue. The skill states this as its single organizing claim; everything else is that claim seen from a different angle.

## What it's optimizing for

**Fewer representable wrong states, not more checks.** The stated aim of `types-are-the-program` is to pick the strongest theorem about the data that's still true - every legal state representable, every illegal one unrepresentable. The concrete move the skill keeps returning to: replace a bag of optionals (`mode: string; path?: string; url?: string`) with a discriminated union where a url-without-auth simply can't be constructed. When that's done, the defensive guards and branches that would have checked for the bad state have nothing to check, so they disappear. That's where the skill's claim of "less code" comes from - constraints absorbing work that sprawl would otherwise do.

**Code that composes because its seams are exact.** The `parts-and-seams` framing says system quality is decided at the boundaries between parts, not inside them. So the skill pushes variability into values crossing one boundary - one `filter(predicate, items)` rather than twenty `filterByX` functions. My reading of the design: this is the concrete engine behind the composability goal. A part whose type is exactly the shape of its legal variability can join with other such parts without an adapter, and the skill's `composability` bar ("a stranger could use this unit without reading its caller") is the test for whether you got there.

**Optimizing carrying cost, not build cost.** `carrying-cost` is stated as a law precisely so the short-term "minimum work to close the ticket" filter can't quietly win. The goal: judge code by what it costs to keep, extend, and reason about forever, and treat the up-front cost of smoothing a piece as cheap against that. The skill spends real length disarming YAGNI and "the wrong abstraction is worse than duplication" - not to reject them, but to scope them to where they apply (crystallized features) and out of where they don't (smooth, composable blocks).

**One authoritative representation per fact.** The `representation` framing gives the truth goals their shape: for any fact there's one canonical map and everything else visibly derives from it, and you prefer maps the machine re-checks (a type, a derived value) over maps a human must remember to update (a comment). This is what `one-source-of-truth`, `single-enforcer`, and `comments-carry-meaning` each apply to a different target - a value, an invariant, a rationale. The `one-source-of-truth` section pins this to a real incident in the author's dotfiles repo where two writers to one file destroyed curated data, to make the point that divergence is a schedule, not a risk.

**Structure follows data flow, not control flow.** `dataflow-not-control-flow` is called out as the most-violated law because every language defaults the wrong way. The goal: the same operations run in the same order every time, and variability lives in the values flowing through. The skill gives a design-time tell for this - if your description of the mechanics contains "if," "and," "when," "skip," or "only," it's probably wrong - so you catch it before writing code, not in review.

**Failures are loud and done has a shape.** `no-silent-failure` and `verifiable-goals` are the process goals: an error must surface rather than be swallowed (`2>/dev/null`, `|| true`, silent fallback data sources are named as bugs on sight), and every goal must have a machine-checkable success criterion that you run yourself rather than handing to the user.

## What it deliberately avoids, and why

**It refuses to be read as a checklist.** The skill says outright that the laws are one coherent way of seeing programs, not items to tick off, and its own header comment forbids deduplicating or compressing the file - it states the redundancy is load-bearing and that distilling a previous version is what destroyed it. So the document repeats the same idea across nineteen laws on purpose; that's a design choice, not an oversight.

**It won't let a local fix launder a bug into silence.** The recurring move it rejects is the one that closes the task faster: the null guard with no else that skips work silently, the sleep that makes a race rarer instead of removing it, the duplicate validation "that can't hurt," the test satisfied by resurrecting dead code. In each case the skill's redirect is to fix the upstream cause - the type that permitted the state, the ordering that isn't owned - rather than patch the symptom. Its stated discipline for this is that polishing is subtraction: a pass that adds a guard or a case is patching, and iterations that grow the code mean you're crystallizing, not smoothing.

**It doesn't claim completeness where it isn't.** The two world-facing laws - `no-ambient-temporal-coupling` and `effects-at-boundaries` - are marked as real but deliberately less elaborated, slated for expansion. The skill flags this as a TODO rather than presenting brevity as a ranking, so a reader doesn't mistake the thin sections for lower-priority laws.
